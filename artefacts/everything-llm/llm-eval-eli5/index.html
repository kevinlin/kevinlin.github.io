LLM Eval

An eval is a repeatable test: a fixed set of tasks, run through a model or an AI app, with every answer graded the same way, so you get a score you can compare after each change.

1 · The problem

You can't tell if a change helped by trying it a few times

LLM output is text that changes from run to run. A fix for one question can quietly break ten others, and a handful of manual tries won't show you that.

It varies

The same input can give different outputs, so one try proves little.

Changes leak

Edit the prompt for one bug and other answers shift too. That's a regression.

"Looks fine" doesn't scale

Reading outputs by hand works for 5 examples. Teams call it a vibe check. It fails at 500.

2 · Analogy

Think of it as a driving test for software that talks

Where the analogy holds
  • The route is fixed, so every driver faces the same test.
  • The examiner uses a checklist, so the result doesn't depend on mood.
  • You can re-test after lessons and see if you improved.
Where it breaks
  • A model can have seen the test questions during training. A driver can't memorise the exact traffic on test day. This is called contamination.
  • You take a driving test once. A model gets re-tested after every change, and its score can move a few points from random noise alone.
  • For open-ended answers the "examiner" is often another LLM, and that examiner makes its own mistakes.

Step 0 of 4

What a test case holds

An input (a question, a document, a task) and a way to judge the answer: an exact expected answer when one exists, or a rubric ("mentions the 14-day limit, does not promise a refund") when it doesn't. A set of these is the dataset or golden set.

What you're actually testing

Rarely the raw model alone. Usually the whole setup: model, system prompt, retrieved documents, tools. Change any one of them and the score can change, so the eval should record which version it ran against.

4 · Grading

Three kinds of grader, each with a blind spot

Use the cheapest grader that can tell right from wrong for that case. Most real evals mix all three.

Code check

Exact match, regex, JSON schema, "do the unit tests pass?"

Costlow
Handles open-ended answerspoor

Blind spot: marks "14 days" wrong when the expected string was "fourteen days".

Model as judge

Another LLM reads the answer and a rubric, then gives pass/fail or a score. Called LLM-as-a-judge.

Costmedium
Handles open-ended answersgood

Blind spot: studies found judges favour longer answers, the first option shown, and sometimes their own model's writing.

Human review

A domain expert reads outputs and labels them.

Costhigh
Handles open-ended answersbest

Blind spot: slow, and two experts often disagree. Best used to check that the model judge agrees with people.

5 · Reading the score

A score is an estimate, and small test sets give fuzzy ones

Model A scores 78%, model B scores 82%. Is B better? Drag the slider to change how many test cases the eval has.

Bars show a rough 95% range: score ± 1.96 × √(p(1−p)/n). It assumes each case is independent; if many cases are variations of the same question, the true range is wider. Running both models on the same cases and comparing case by case (a paired comparison) cuts the noise.

6 · Agents and retries

"Solved it once" and "solves it every time" are different numbers

When a task can be retried, evals report one of two metrics. They answer different questions. Below, each try succeeds with the chance you set, and tries are treated as independent.

pass@k
pass^k

pass@k = at least one of k tries works = 1 − (1−p)k. Fits a coding tool where a developer picks the one that works.

pass^k = all k tries work = pk. Fits a customer-facing agent where every conversation has to go right.

Agent evals also grade differently: the useful check is often the end state ("was the booking actually created?") instead of the wording of the final message.

7 · Benchmarks vs your evals

Leaderboard scores tell you little about your own use case

Public benchmarkYour own eval
ExamplesMMLU, GPQA, SWE-bench50–500 cases pulled from your real traffic and bug reports
Answers"Which model is generally stronger?""Did my change make my product better or worse?"
Main riskContamination (questions leaked into training data) and saturation (top models all near 100%, so the test stops separating them)Cases drift away from what users actually ask; the set needs updating

Goodhart's law

"When a measure becomes a target, it ceases to be a good measure." If you tune a prompt until it passes your 50 cases, it may just be fitted to those 50. Keep some cases held back that you don't tune against.

8 · Common mix-ups

Mistakes that give people the wrong picture

"A high benchmark score means it'll work for us."

Benchmarks test general skill on someone else's tasks. Your domain, format rules and edge cases need your own cases.

"We need thousands of cases before we start."

A few dozen cases taken from real failures already catch regressions. Grow the set each time you find a new bug.

"The LLM judge is objective."

It has biases of its own. Check it against a sample of human labels before trusting its scores.

"One number sums it up."

An average hides which cases broke. Read the failing outputs; that's where the fixes come from.

9 · When it pays off

Build an eval before you need to answer these

Swapping models

A new model version ships. Is it safe to switch?

Editing prompts

You fixed one bug. What else moved?

Shipping to users

Is it good enough, and how often does it fail?

Less useful: a one-off script you'll run once and check by eye. The eval would cost more than the checking.

Summary

Remember this

Fixed cases → run the whole system → grade each answer the same way → read the score together with its error range and the failing cases. Rerun after every change. Your own cases tell you more than any leaderboard.
