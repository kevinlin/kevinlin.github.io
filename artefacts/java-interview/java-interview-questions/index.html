AI skills and engineering quality

9 questions
01 We have a Skill that updates repositories. How do you make sure it works across different repos?Tap to reveal

I would treat the Skill like a software product rather than only a prompt.

Different repositories have different languages and framework versions, build systems, directory structures, coding conventions, test frameworks, dependency-management tools, and CI pipelines.

So I would separate the Skill into roughly three stages:

Discover → Change → Verify

First, Discover the repository deterministically:

  • Detect language and framework versions
  • Identify Maven, Gradle, npm, pnpm, and similar tools
  • Read repository-specific instructions
  • Identify build, test, and lint commands
  • Detect dependency constraints

Second, Change using the appropriate strategy for that repository.

Third, Verify using the repository's own engineering controls:

compile
→ lint
→ static analysis
→ unit tests
→ integration tests
→ dependency/security scan
→ inspect diff

I would also maintain a set of representative test repositories, effectively an evaluation suite for the Skill. Every Skill change should run against those repositories before release.

Don't test whether the LLM produced a convincing answer. Test whether the resulting repository still builds and satisfies its engineering contracts.
02 Our vulnerability Skill gives different results every time we run it. How would you fix that?Tap to reveal

I would first identify where the nondeterminism comes from. Possible sources include:

  • Different model versions
  • Temperature or sampling
  • Different files entering the context
  • Files discovered in different order
  • Search results changing
  • Tool versions changing
  • Dependencies being resolved differently
  • Prompt ambiguity
  • The LLM itself being used for deterministic analysis

Then I would reduce the amount of work delegated to the LLM. For vulnerability discovery, established deterministic tools should do as much as possible:

Repository
    ↓
SAST / SCA / secret scanner / dependency scanner
    ↓
Structured findings
    ↓
LLM reasoning and triage
    ↓
Validated findings

For example, the Skill could orchestrate Semgrep, CodeQL, dependency scanners, and repository inspection. The LLM can then correlate and explain findings.

I would also pin the Skill version, model version where possible, tool versions, dependency versions, prompt and instructions, and the repository commit SHA. And I would make file discovery deterministic by sorting paths and explicitly defining inclusion and exclusion rules.

Finally, I would create a golden evaluation set:

Repo A → expected vulnerabilities
Repo B → expected vulnerabilities
Repo C → expected no-findings

Then measure precision, recall, and run-to-run variance. For a security Skill, reproducibility should be a measurable quality attribute.

The solution is to constrain AI-generated code with the same engineering controls we apply to human-written code:

AI can generate code quickly, but correctness must come from deterministic engineering feedback loops.
04 Engineers use an LLM to fix bugs they could easily solve themselves. Is that a problem?Tap to reveal

Not necessarily.

I don't measure AI adoption by how frequently developers use an LLM. I measure whether it improves engineering outcomes. For a simple bug, asking an LLM may actually take longer than fixing it directly.

I encourage engineers to decide based on the task. AI is particularly useful for:

  • Exploring an unfamiliar codebase
  • Finding dependencies
  • Generating repetitive changes
  • Generating tests
  • Large-scale refactoring
  • Comparing implementation options
  • Documentation
  • Root-cause hypothesis generation

But engineers still need to understand the code. One risk is becoming dependent on AI without developing engineering judgment. I want AI to amplify engineering capability, not replace understanding.

06 How would you use AI to migrate MongoDB to Oracle?Tap to reveal

I would use AI to accelerate analysis and implementation, but not let an LLM independently move production data.

First I would profile the MongoDB data: collections, document shapes, optional fields, nested objects, arrays, relationships, data volumes, indexes, and query patterns.

Then define the target relational model explicitly:

Mongo document
    ↓
Schema inference
    ↓
Relational model
    ↓
Mapping specification
    ↓
Transformation code
    ↓
Migration
    ↓

AI can help with:

  • Generating Oracle DDL
  • Generating transformation code
  • Generating migration scripts
  • Generating data-quality tests

source count == target count

07 React Redux and Spring Boot contain substantial boilerplate. Can AI help?Tap to reveal

Yes. This is one of the areas where I have applied AI-assisted development.

For React and Redux, AI can help generate typed components and hooks, Redux Toolkit slices, selectors, async thunks, RTK Query endpoints, form validation, API clients, reducer and component tests, migration from legacy connect code to hooks, and Storybook stories.

For Spring Boot, AI can help generate controllers, services, and repositories, request and response DTOs, entity-to-DTO mappers, validation rules, JPA queries, database migrations, unit and integration tests, Testcontainers setup, OpenAPI definitions and clients, and deployment manifests.

However, I would first reduce unnecessary boilerplate through framework capabilities such as Redux Toolkit, Spring Data, Java records, MapStruct, and OpenAPI code generation. AI should complement these tools, not create large amounts of code that the framework can already generate.

My normal workflow is:

  1. Give the AI the repository conventions and relevant examples.
  2. Ask it to make a small, scoped change.
  3. Review the generated design and code.
  4. Run compilation, linting, tests, and security checks.
  5. Inspect the diff manually.
  6. Correct the result and capture reusable instructions.

AI is particularly useful for repetitive code, test coverage, codebase discovery, refactoring, and documentation. But developers remain responsible for business correctness, security, performance, and maintainability.

08 How would you use AI safely in a bank?Tap to reveal

I would only use bank-approved models and tools, and I would follow the organization's rules for source code, production data, personal data, and confidential information.

I would also apply engineering controls:

  • Keep generated changes small and reviewable
  • Require human review

  • Validate authorization and data-access behaviour
  • Keep an audit trail through normal version control
  • Measure whether AI improves quality and delivery rather than assuming it does

The goal is not to let AI independently write the system. The goal is to help engineers understand, implement, test, and review changes more efficiently.

Java 17 to 21 and virtual threads

10 questions
10 Which Java 17 to 21 features have you used?Tap to reveal

I have mainly used Java 17 features in production and followed the newer features introduced up to Java 21.

Features I have used or evaluated include:

  • Records for immutable data-transfer objects
  • Sealed classes for controlled type hierarchies
  • Pattern matching for instanceof
  • Switch expressions and pattern matching for switch
  • Text blocks for SQL, JSON, and test data
  • Virtual threads in Java 21 for high-concurrency, I/O-heavy workloads

For example, records reduce boilerplate for request and response models:

public record CustomerResponse(
    String id,
    String name,
    String status
) {}

Virtual threads are useful when an application performs many blocking calls, such as database queries or downstream HTTP requests. But I would still validate library compatibility, connection-pool limits, observability, and actual performance before adopting them.

11 What are virtual threads?Tap to reveal

Virtual threads were introduced as a production feature in Java 21.

Traditional Java platform threads are relatively expensive because they are closely associated with OS threads.

Virtual threads are lightweight JVM-managed threads. Instead of:

1 request
   ↓
1 heavyweight OS-backed thread

we can have very large numbers of lightweight virtual threads multiplexed over a smaller set of carrier threads.

They are particularly useful for I/O-bound applications that spend time waiting on:

  • Database calls
  • HTTP APIs
  • Files
  • Messaging
  • Other network I/O

They allow us to continue writing straightforward blocking code rather than necessarily moving to a reactive programming model.

12 Have you used virtual threads from Java 21?Tap to reveal

I have experimented with virtual threads and understand how to apply them, although I have not yet used them extensively in a production system.

For example:

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    var futures = IntStream.range(0, 1_000)
        .mapToObj(i -> executor.submit(() -> callRemoteService(i)))
        .toList();

    for (var future : futures) {
        future.get();
    }
}

The main benefit is that we can continue using a straightforward blocking programming model without maintaining large platform-thread pools. Oracle recommends treating each concurrent task as a virtual thread rather than pooling virtual threads.

With Spring Boot on Java 21 or later, virtual threads can be enabled with:

spring.threads.virtual.enabled=true

Spring Boot can then use virtual threads for its auto-configured task executor.

I would still test it carefully because virtual threads do not:

  • Make CPU-bound work faster
  • Increase database connection-pool capacity
  • Remove downstream API limits
  • Replace backpressure or rate limiting
  • Automatically fix poor concurrency design

I would monitor thread count, database-pool saturation, HTTP connection pools, latency, throughput, and memory before and after enabling them.

13 How are virtual threads different from regular platform threads?Tap to reveal

The programming interface looks very similar because both are Java Threads. The major difference is implementation and cost.

Platform thread

Java Thread
     ↓
OS Thread

Relatively expensive and therefore commonly pooled.

Virtual thread

Many Virtual Threads
        ↓
JVM scheduler
        ↓
Few carrier/platform threads
        ↓
OS threads

A virtual thread can be parked when it performs supported blocking I/O, allowing the carrier thread to run something else.

But virtual threads do not provide additional CPU capacity. If I have eight CPU cores and CPU-intensive work, creating 100,000 virtual threads will not make the computation faster.

They primarily improve scalability for blocking I/O workloads.

14 How are Java virtual threads similar to Go goroutines?Tap to reveal

The mental model is similar. Both allow large numbers of lightweight concurrent tasks and let the runtime schedule them onto a smaller number of operating-system threads. That makes the concept familiar to someone who has worked with Go.

However, they are not identical.

Go encourages goroutines together with channels and select.

Java virtual threads deliberately preserve Java's normal thread and blocking programming model. Existing blocking code, debugging tools, stack traces, and thread-based APIs generally continue to work, so existing Java developers can use constructs such as:

Thread.startVirtualThread(() -> processRequest());

without rewriting the entire application around asynchronous callbacks.

15 Would virtual threads solve a service receiving thousands of concurrent requests?Tap to reveal

They may help if the application is primarily I/O-bound, but they are only one part of the solution.

For example:

4,000 virtual threads
        ↓
Database pool: 50 connections

The database still only handles roughly 50 concurrent database operations.

So I would also examine:

  • Database connection pool
  • HTTP connection pool
  • Downstream service limits
  • Rate limiting
  • Backpressure
  • CPU
  • Memory
  • Database query performance

Virtual threads can remove the application thread pool as a bottleneck. They cannot remove bottlenecks downstream.

16 When should virtual threads not be used?Tap to reveal

Virtual threads are mainly useful for workloads that spend significant time waiting for I/O.

They do not improve CPU-intensive work such as encryption, image processing, or complex calculations. CPU-bound work is still limited by the available CPU cores.

I would also check:

  • Database connection-pool limits
  • Downstream service concurrency limits
  • HTTP client connection limits
  • Thread-local usage
  • Synchronization and native calls
  • Observability-tool support

For example, creating 10,000 virtual threads does not help if the database pool only allows 20 active connections. It may simply create 9,980 tasks waiting for connections.

17 What is a Java record?Tap to reveal

A record is a concise way to represent an immutable data carrier.

Instead of writing:

public class CustomerDto {
    private final String id;
    private final String name;

    // constructor
    // getters
    // equals
    // hashCode
    // toString
}

I can write:

public record CustomerDto(
    String id,
    String name
) {}

Java automatically provides the constructor, accessors, equals, hashCode, and toString.

18 When would you use records?Tap to reveal

I use records for immutable data carriers, such as:

  • API request and response objects
  • DTOs
  • Domain events
  • Query results
  • Value objects and configuration values

I would generally not use records directly as traditional mutable JPA entities because the persistence model has different requirements: JPA entities usually need mutable state, proxying, and a no-argument constructor. Records are a better fit at application boundaries than as persistence entities.

19 What problem do sealed classes solve?Tap to reveal

Sealed classes restrict which classes can extend or implement a type. They are useful when the domain has a known set of variants.

For example:

public sealed interface PaymentResult
    permits PaymentSucceeded, PaymentFailed {
}

public record PaymentSucceeded(String transactionId)
    implements PaymentResult {
}

public record PaymentFailed(String reason)
    implements PaymentResult {
}

This makes the model clearer and allows exhaustive switch handling.

Spring IoC, beans, and lifecycle

10 questions
20 What is inversion of control?Tap to reveal

Inversion of control means that control over object creation, configuration, and lifecycle is transferred from application code to a container or framework.

Without IoC, a service constructs its own dependencies:

public class PaymentService {
    private final PaymentRepository repository =
        new JpaPaymentRepository();
}

With Spring IoC, the service declares what it needs, and Spring supplies it:

@Service
public class PaymentService {

    private final PaymentRepository repository;

    public PaymentService(PaymentRepository repository) {
        this.repository = repository;
    }
}

This gives us lower coupling, easier unit testing, explicit dependencies, centralized configuration, framework-managed lifecycle, and easier replacement of implementations.

I normally prefer constructor injection because required dependencies are visible and fields can remain final.

21 What is the difference between IoC and dependency injection?Tap to reveal

IoC is the broader principle. Dependency injection is one technique used to implement IoC.

With dependency injection, dependencies are supplied to an object instead of being created by the object itself.

22 Why do you prefer constructor injection?Tap to reveal

I prefer constructor injection because:

  • Required dependencies are explicit
  • The object cannot be created in an invalid state
  • Fields can be final
  • Unit tests can instantiate the class directly
  • It avoids hidden dependencies
  • It helps identify classes with too many responsibilities

Field injection is less explicit and makes plain unit testing harder.

Bean post-processors are important because many Spring capabilities are implemented around this lifecycle, including proxy creation. Post-initialization processing is where Spring may return a proxied object for features such as AOP and transactions.

25 Does Spring manage every bean lifecycle in the same way?Tap to reveal

No. The lifecycle depends partly on the bean scope.

For a singleton bean, Spring normally manages creation, initialization, and destruction.

For a prototype bean, Spring creates and initializes the object, but it does not normally manage its complete destruction lifecycle after handing the object to the caller.

Web applications can also use request and session scopes, where the bean lifecycle follows the HTTP request or user session.

26 What is a BeanPostProcessor?Tap to reveal

A BeanPostProcessor allows Spring or application code to inspect or modify bean instances before and after initialization.

Spring uses bean post-processors for features such as dependency injection annotations, lifecycle annotations, AOP proxies, transactional proxies, security proxies, and custom framework integration.

For example, Spring can detect @Autowired, @PostConstruct, and proxy-related annotations through post-processors rather than putting that logic directly into every bean.

27 What happens when Spring finds multiple beans of the same type?Tap to reveal

Spring cannot decide which bean to inject and normally throws NoUniqueBeanDefinitionException.

I can resolve this using @Qualifier, @Primary, injecting a collection of implementations, or improving the application design so the required implementation is explicit.

Example:

@Service
class PaymentService {
    PaymentService(
        @Qualifier("stripePaymentClient")
        PaymentClient paymentClient
    ) {
    }
}
28 What are common Spring bean scopes?Tap to reveal

The main scopes are:

  • singleton: one bean instance per Spring application context
  • prototype: a new instance each time it is requested
  • request: one instance per HTTP request
  • session: one instance per HTTP session

Most stateless services are singleton beans. Therefore, I avoid storing request-specific mutable state inside them.

29 What is a circular dependency, and how would you fix it?Tap to reveal

A circular dependency occurs when bean A depends on bean B and bean B depends on bean A.

I would normally treat it as a design issue rather than solve it using @Lazy. Typical fixes include:

  • Extracting shared logic into a third service
  • Introducing an event
  • Reversing or clarifying the dependency direction
  • Separating orchestration from domain logic

Spring transactions and propagation

8 questions
30 What is a transaction?Tap to reveal

A database transaction groups operations into one logical unit of work.

The classic properties are ACID: atomicity, consistency, isolation, and durability.

For example, transferring money might require:

debit Account A
credit Account B
write transaction record

Either all operations commit or the transaction should roll back.

31 How does @Transactional work in Spring?Tap to reveal

Spring normally implements declarative transactions through an AOP proxy.

For example:

@Service
public class PaymentService {

    @Transactional
    public void processPayment() {
        ...
    }
}

Conceptually:

Caller
  ↓
Spring transaction proxy
  ↓
Begin transaction
  ↓
processPayment()
  ↓
Commit / rollback

By default, @Transactional uses Propagation.REQUIRED.

One important detail is that Spring's normal proxy-based transaction handling intercepts external calls through the proxy. Self-invocation within the same object does not trigger another transactional interceptor.

32 What is transaction propagation?Tap to reveal

Propagation determines what happens when a transactional method calls another method while a transaction already exists.

PropagationBehaviour
REQUIREDJoin existing transaction, otherwise create one
REQUIRES_NEWSuspend existing transaction and create another
NESTEDUse a nested transaction or savepoint where supported
SUPPORTSJoin if one exists, otherwise run without one
MANDATORYRequire an existing transaction
NOT_SUPPORTEDSuspend transaction and run without one
NEVERFail if a transaction exists

REQUIRED is the default. REQUIRES_NEW creates an independent transaction and suspends the outer one.

33 Is putting @Transactional on the top-level method sufficient?Tap to reveal

Often, yes, if all called database operations are supposed to participate in the same transaction.

For example:

@Transactional
public void placeOrder() {
    reserveInventory();
    saveOrder();
    createPayment();
}

All database work on the same transaction manager can participate in that transaction.

But there are important exceptions. If an inner method requires REQUIRES_NEW, different isolation, a different transaction manager, or a separate rollback boundary, then the inner transaction configuration needs to be applied correctly.

There is also the Spring proxy issue:

public void outer() {
    inner();
}

@Transactional(propagation = REQUIRES_NEW)
public void inner() {
}

If outer() and inner() are methods of the same object, inner() is called directly rather than through the Spring proxy. Therefore the REQUIRES_NEW behaviour may not be applied.

A common solution is to move the inner operation into a separate Spring service.

34 What happens with REQUIRED?Tap to reveal

Consider:

@Transactional
public void createOrder() {
    paymentService.reservePayment();
}

and:

@Transactional
public void reservePayment() {
}

Since REQUIRED is the default:

createOrder transaction
        ↓
reservePayment joins same transaction

If an unchecked exception causes the transaction to roll back:

Order changes      rollback
Payment changes    rollback

They are part of the same physical transaction.

35 What happens with REQUIRES_NEW?Tap to reveal

Consider:

@Transactional
public void createOrder() {
    auditService.writeAudit();
    throw new RuntimeException();
}

and:

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void writeAudit() {
    ...
}

Assuming auditService is another proxied Spring bean:

Outer transaction starts
        ↓
Outer transaction suspended
        ↓
New audit transaction starts
        ↓
Audit transaction commits
        ↓
Outer transaction resumes
        ↓
Outer transaction fails
        ↓
Outer transaction rolls back

The audit record remains committed because it used an independent transaction.

This can be useful for audit records, independent status updates, and failure logging. But I use it carefully because it changes atomicity.

36 If REQUIRES_NEW fails, does the outer transaction also roll back?Tap to reveal

Not automatically, because they are separate transactions. The inner transaction rolls back independently.

But if its exception propagates back into the outer transactional method, Spring will normally mark the outer transaction for rollback as well:

Inner REQUIRES_NEW
    ↓
exception
    ↓
inner rollback
    ↓
exception propagates
    ↓
outer rollback

If the outer method intentionally catches and handles the exception:

try {
    auditService.writeAudit();
} catch (Exception e) {
    // handle it
}

then the outer transaction can potentially continue and commit. The exact desired behaviour should be intentional.

37 Is there any resource issue with REQUIRES_NEW?Tap to reveal

Yes.

The outer transaction may continue holding a database connection while the inner REQUIRES_NEW transaction needs another one. Under heavy concurrency this can exhaust the connection pool.

For example:

100 concurrent outer transactions
100 DB connections already held

Each calls REQUIRES_NEW
        ↓
Needs another 100 connections

So transaction propagation has performance and capacity implications, not just code-level semantics.

JPA, Hibernate, and JDBC

14 questions
38 What is the difference between JPA, Hibernate, and JDBC?Tap to reveal

They operate at different abstraction levels.

JDBC

Low-level Java API for interacting directly with relational databases. I control:

SQL
parameters
ResultSet mapping
connections
statements

JPA

A Java persistence specification defining concepts such as entity, EntityManager, persistence context, relationships, and transactions.

Hibernate

A popular implementation of JPA that also provides additional features beyond the standard.

So:

Application
    ↓
JPA API
    ↓
Hibernate
    ↓
JDBC
    ↓
Database

I normally code against JPA abstractions where practical, while understanding Hibernate-specific behaviour such as proxies, dirty checking, batching, and fetch strategies.

39 When would you use JPA/Hibernate versus JDBC?Tap to reveal

I would use JPA/Hibernate when:

  • The application has a rich relational domain model
  • CRUD is a large part of the workload
  • Entity relationships are useful
  • Developer productivity matters
  • Dirty checking and the persistence context help
  • Queries are relatively conventional

I would consider JDBC or JdbcTemplate when:

  • I need very precise SQL control
  • I have complex analytical queries
  • I am processing large volumes
  • I need high-performance bulk inserts or updates
  • Object graph mapping adds little value
  • Predictable database behaviour is more important than ORM convenience

I don't see this as an either/or decision. A Spring Boot service can use JPA for normal domain persistence and JDBC for a performance-sensitive batch operation.

40 Why can Hibernate become problematic at high data volumes?Tap to reveal

Hibernate manages entities inside a persistence context.

If I load hundreds of thousands of records into one transaction, Hibernate may keep many managed objects in memory. That can lead to:

  • High heap usage
  • Dirty-checking overhead
  • Long transactions
  • Large flush operations
  • GC pressure

For bulk processing I might instead use pagination, streaming, JDBC batching, flush() and clear(), stateless Hibernate sessions, native SQL, or Spring Batch.

The choice depends on workload.

41 How would you design a one-to-many relationship?Tap to reveal

Consider Customer 1 → N Orders.

At the database level, I would normally place the foreign key on the many side:

orders.customer_id

In JPA:

@Entity
class Order {

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "customer_id")
    private Customer customer;
}

And if I genuinely need bidirectional navigation:

@Entity
class Customer {

    @OneToMany(mappedBy = "customer")
    private List<Order> orders;
}

The Order side owns the relationship because it contains the foreign key.

I would normally prefer lazy loading and query based on the use case rather than automatically retrieving the entire object graph.

42 What is the owning side of a JPA relationship?Tap to reveal

The owning side controls the foreign-key relationship from JPA's perspective.

In a bidirectional relationship, the side without mappedBy is usually the owning side.

For example:

@Entity
class OrderItem {
    @ManyToOne
    @JoinColumn(name = "order_id")
    private Order order;
}

@Entity
class Order {
    @OneToMany(mappedBy = "order")
    private List<OrderItem> items;
}

OrderItem owns the relationship because it contains the foreign key.

43 How would you fetch one-to-many data without creating an N+1 problem?Tap to reveal

Suppose I fetch 100 customers and then access their orders. A naive implementation could generate:

1 query for customers
+
100 queries for orders
=
101 queries

I would first identify what the API actually needs. Options include:

  • Fetch join
  • EntityGraph
  • DTO projection
  • Batch fetching
  • Explicit query
  • Separate batched queries

For an API response, I often prefer a DTO projection tailored to the endpoint rather than returning persistence entities directly.

I also need to be careful with pagination. Fetch-joining large collections can produce huge Cartesian result sets and make pagination difficult.

44 What is the N+1 query problem?Tap to reveal

The N+1 problem occurs when one query loads a collection of parent records, followed by one additional query for each parent.

For example:

List<Order> orders = orderRepository.findAll();

for (Order order : orders) {
    order.getItems().size();
}

This may execute one query for orders and N queries for their items.

I would diagnose it through SQL logging, APM tracing, or Hibernate statistics. Possible solutions include fetch joins, entity graphs, batch fetching, DTO projections, or redesigning the query around the actual use case.

45 What are the JPA entity lifecycle states?Tap to reveal

The common JPA entity states are:

  • Transient: a normal Java object not managed by JPA
  • Managed or persistent: tracked by the persistence context
  • Detached: previously managed but no longer tracked
  • Removed: marked for deletion

A managed entity is automatically checked for changes. Hibernate can generate an update during transaction commit without an explicit update call.

46 What is dirty checking?Tap to reveal

Dirty checking means Hibernate tracks changes to managed entities. At flush or commit time, it compares their current state with the original state and generates the required SQL updates.

For example:

@Transactional
public void renameCustomer(Long id, String name) {
    Customer customer = repository.findById(id)
        .orElseThrow();

    customer.setName(name);
}

An explicit save may not be required because the entity is managed.

47 What is the difference between LAZY and EAGER fetching?Tap to reveal

LAZY loading retrieves the related entity only when it is accessed. EAGER loading retrieves it as part of the initial operation, although the exact SQL strategy depends on the provider.

I prefer lazy loading for most relationships because eager loading can retrieve unnecessary data and produce large object graphs.

But lazy loading must be handled carefully because it can cause:

  • N+1 queries
  • LazyInitializationException
  • Unexpected database access during serialization

I use fetch joins, entity graphs, DTO projections, or dedicated queries depending on the use case.

48 What is the difference between persist, merge, and save?Tap to reveal

persist makes a new entity managed. It returns void.

merge copies state from a detached object into a managed entity and returns that managed instance. The object passed into merge does not itself become managed.

save is a Spring Data abstraction. Depending on whether the entity is considered new, it generally delegates to either persist or merge.

49 What problems can CascadeType.ALL cause?Tap to reveal

CascadeType.ALL includes persist, merge, remove, refresh, and detach.

It can be dangerous when applied without considering aggregate boundaries. In particular, cascading remove may delete related records unexpectedly.

I use cascading only when the child lifecycle is genuinely owned by the parent. For shared entities, I avoid cascading remove.

50 What is optimistic locking?Tap to reveal

Optimistic locking prevents lost updates without holding a database lock for the full transaction.

JPA commonly uses a version field:

@Version
private Long version;

When two transactions update the same entity, the second transaction may fail with an optimistic-lock exception because its version is outdated.

It is suitable when conflicts are possible but not frequent.

51 How would you improve JPA performance?Tap to reveal

I would first measure the problem through SQL logs, query plans, Hibernate statistics, or application tracing.

Common improvements include:

  • Avoiding N+1 queries
  • Selecting only required columns using DTO projections
  • Using pagination
  • Adding appropriate database indexes
  • Enabling JDBC batching
  • Controlling fetch plans
  • Avoiding unnecessarily large persistence contexts
  • Using read-only transactions for read operations
  • Avoiding entity serialization directly from controllers
  • Reviewing connection-pool sizing

React and Redux

7 questions
52 Explain React.Tap to reveal

React is a library for building user interfaces from reusable components.

A component receives data through props, maintains local state where necessary, and declares what the UI should look like. When state changes, React re-renders the relevant component tree and reconciles the result with the DOM.

Important concepts include components, props, state, hooks, one-way data flow, component composition, effects, context, and reconciliation.

For example:

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(c => c + 1)}>
      {count}
    </button>
  );
}

I normally keep state as close as possible to where it is used and only move it into shared state when multiple components genuinely require it.

53 What is a controlled versus uncontrolled component in React?Tap to reveal

A controlled component has its state controlled by React:

function NameInput() {
  const [name, setName] = useState("");

  return (
    <input
      value={name}
      onChange={e => setName(e.target.value)}
    />
  );
}

React state is the source of truth.

An uncontrolled component stores the current value in the DOM:

function NameInput() {
  const inputRef = useRef<HTMLInputElement>(null);

  return <input ref={inputRef} />;
}

Then I can access it using inputRef.current?.value.

Controlled

Useful when I need validation, dynamic UI behaviour, immediate state synchronization, or form logic that depends on the value.

Uncontrolled

Useful when the input is simple, I only need the value on submission, I am integrating with DOM-oriented libraries, or I am managing file inputs.

For most business forms, I generally prefer controlled inputs or a form library that efficiently manages the same concerns.

54 What is ReactJS versus React Native?Tap to reveal

ReactJS and React Native share the React programming model: components, props, state, hooks, and context.

But the rendering targets are different.

ReactJS normally renders to the browser DOM:

<div>
<button>
<input>

React Native renders native platform components:

<View>
<Text>
<Pressable>

React Native does not simply render HTML inside a mobile application. React coordinates native UI components on iOS and Android.

Business logic and some hooks can often be shared, but UI components and platform APIs frequently differ.

55 What is React versus JSX?Tap to reveal

React is the UI library.

JSX is syntax commonly used to describe React elements:

const element = <button>Save</button>;

Conceptually, JSX is transformed into JavaScript that creates React elements.

You can technically use React without JSX, but JSX makes component trees much easier to read and maintain.

56 Explain Redux.Tap to reveal

Redux manages shared application state using predictable one-way data flow.

The main concepts are store, state, action, reducer, dispatch, selector, and middleware.

The flow is:

UI
 ↓
dispatch(action)
 ↓
reducer
 ↓
new state
 ↓
UI re-renders

With modern Redux, I would use Redux Toolkit rather than manually creating large numbers of action constants and reducers:

const counterSlice = createSlice({
  name: "counter",
  initialState: { value: 0 },
  reducers: {
    increment: state => {
      state.value++;
    }
  }
});

React components normally read from the store using React-Redux hooks such as useSelector and useDispatch.

I would use Redux for genuinely shared application state, rather than putting every local UI state into the store.

57 When would you use Redux?Tap to reveal

I would use Redux when the application has complex shared state that must be accessed and updated across different screens or components.

Examples include:

  • Authenticated-user information
  • Complex workflow state
  • Shared filters and search criteria
  • Cached server responses
  • Application-wide notifications
  • State that needs debugging, auditing, or predictable transitions

I would not put every piece of state into Redux. Temporary UI state such as whether a dialog is open can normally remain inside the component.

For server state, I would also consider RTK Query or another query-management solution rather than manually implementing loading, caching, invalidation, and error handling.

58 Why does Redux have a reputation for boilerplate?Tap to reveal

Older Redux implementations often required separate files and code for action-type constants, action creators, reducers, immutable state updates, selectors, thunks, and store configuration.

Modern Redux Toolkit reduces much of that boilerplate through createSlice, configureStore, createAsyncThunk, and RTK Query. The Redux documentation recommends Redux Toolkit as the standard way to write Redux applications today.

However, if the team already has an established Redux architecture, I would first understand its conventions. I would not introduce a large migration merely because a newer pattern exists. Changes should be incremental and supported by tests.

Kafka, JMS, and compatibility

7 questions
59 What is a Kafka topic versus a queue?Tap to reveal

Kafka has topics rather than a separate queue primitive.

Queue-like behaviour comes from consumers sharing the same consumer group:

Topic
 ├ Partition 0 → Worker A
 ├ Partition 1 → Worker B
 └ Partition 2 → Worker C

Each partition is handled by one consumer within that group.

Publish-subscribe behaviour comes from multiple consumer groups:

OrderCreated
   ├ Inventory group
   ├ Notification group
   └ Analytics group

Each group independently receives the events.

60 I need to rename a Kafka topic used by multiple teams. How do I prevent consumer applications from breaking?Tap to reveal

I would treat a topic rename as a contract migration, not a simple rename. Kafka does not provide a transparent alias that makes this safe automatically.

I would create a new topic and use a staged migration:

             ┌ old-topic → old consumers
Producer ────┤
             └ new-topic → migrated consumers

Phase 1: Prepare

  • Create the new topic
  • Match partitioning where appropriate
  • Configure ACLs
  • Ensure schemas are compatible
  • Inform consumer teams

Phase 2: Dual publish or bridge

Temporarily publish events to both old and new topics, or introduce a controlled replication or bridge process.

Phase 3: Consumer migration

Teams migrate independently:

Consumer A → new topic
Consumer B → new topic
Consumer C → old topic

Phase 4: Observe

Monitor consumer lag, message counts, errors, and remaining consumption from the old topic.

Phase 5: Deprecate

Only after no consumers depend on the old topic: stop dual publishing, retain the old topic for an agreed period, remove ACLs, and delete it later.

The key is backward compatibility and an explicit deprecation window.

61 When would you use Kafka?Tap to reveal

I would use Kafka when the system needs:

  • High-throughput event streaming
  • Durable event history
  • Multiple independent consumers
  • Replay of past events
  • Stream processing
  • Loose coupling between producers and consumers
  • Partition-based horizontal scaling

Examples include domain events, activity streams, audit pipelines, analytics ingestion, and change-data capture.

62 When would you use JMS?Tap to reveal

I would use JMS when the application needs traditional enterprise messaging, especially:

  • Work queues
  • Reliable command delivery
  • Transactional messaging
  • Integration with existing enterprise systems
  • Request-reply messaging
  • Broker features such as selectors or dead-letter queues

JMS is an API specification, not a message broker. Implementations include ActiveMQ Artemis and IBM MQ.

63 What is the main difference between Kafka and JMS?Tap to reveal

Kafka is a distributed event log. Messages are retained according to a retention policy, even after they are consumed. Consumers track their own positions and can replay events.

Traditional JMS brokers are usually focused on delivering messages to consumers. A queue message is typically removed after successful acknowledgement.

Kafka is strong for event streams and replay. JMS is strong for enterprise messaging and command-oriented workflows.

The choice should be based on delivery semantics, ordering, replay requirements, operational environment, and integration constraints.

64 Can Kafka replace JMS?Tap to reveal

Not in every case.

Kafka can support many asynchronous messaging use cases, but JMS brokers may be more suitable when the system needs:

  • Strong request-reply patterns
  • Message selectors
  • Broker-managed per-message delivery
  • Integration with existing JMS-based systems
  • Traditional distributed transaction support
  • Simple work queues with individual-message acknowledgement

I would not replace JMS with Kafka only because Kafka is newer. I would first understand the messaging semantics.

65 When would you use Kafka instead of a traditional queue?Tap to reveal

I would prefer Kafka when the system needs high-throughput event streaming, retained event history, replay, multiple independent consumers, partition-based scaling, stream processing, or event-driven integration.

I would consider a traditional JMS queue when the use case is primarily command delivery, request-reply, integration with existing enterprise middleware, or broker-managed message-routing features.

The decision should be based on required semantics, not only throughput or technology preference.

Queue versus topic

7 questions
66 What is the difference between a queue and a topic?Tap to reveal

A queue normally uses point-to-point messaging. Each message is processed by one consumer from the competing consumer group.

A topic normally uses publish-subscribe messaging. Each subscription receives its own copy of the message.

For example:

  • Queue: process an invoice exactly once by one worker
  • Topic: publish an OrderCreated event to inventory, notification, analytics, and fraud services
67 What is the difference between a JMS queue and a JMS topic?Tap to reveal

A JMS queue normally implements point-to-point messaging. One message is processed by one consumer.

A JMS topic implements publish-subscribe messaging. Every active or durable subscription can receive the message.

Examples:

  • A queue is suitable for assigning a payment-processing job to one worker.
  • A topic is suitable for publishing an OrderCreated event to inventory, notification, and analytics services.

In Kafka, both patterns can be implemented using topics and consumer groups.

68 If several consumers listen to a queue, who receives the message?Tap to reveal

Normally, one consumer receives each message. Consumers compete for messages, which allows horizontal scaling.

The exact delivery and redelivery behaviour depends on acknowledgements, transactions, and broker configuration.

69 How is a Kafka topic different from a JMS topic?Tap to reveal

A Kafka topic is divided into partitions and acts as a retained log. Consumer groups independently track offsets. Events can be replayed while they remain within the retention period.

A JMS topic generally sends messages to active subscriptions. Durable subscriptions allow consumers to receive messages that were published while they were disconnected, but the model is still different from Kafka's log and offset model.

70 How do you preserve message ordering in Kafka?Tap to reveal

Kafka guarantees ordering within a partition, not across the whole topic.

To preserve ordering for a particular entity, I use a stable partition key, such as customerId or orderId. Events with the same key go to the same partition.

The trade-off is that one hot key can limit scalability.

71 How do you handle duplicate message processing?Tap to reveal

I design consumers to be idempotent because duplicates can occur during retries or failure recovery.

Common approaches include:

  • A processed-message table keyed by event ID
  • Unique database constraints
  • Idempotency keys
  • Upserts
  • State-transition validation
  • Transactional outbox and inbox patterns

I would not rely only on the broker's "exactly once" terminology. End-to-end processing also includes database writes and downstream calls.

72 What is a dead-letter queue?Tap to reveal

A dead-letter queue stores messages that could not be processed after a configured number of attempts.

I would include the original message, error details, attempt count, timestamp, consumer or service name, and correlation ID.

I would also distinguish transient failures from permanent failures. Transient errors may be retried with backoff, while invalid business data should normally go directly to a dead-letter path.

76 Java is being used for everything, but performance is a concern. How would you approach that discussion?Tap to reveal

I would avoid starting from the language choice. I would first measure where the bottleneck actually is.

  • Database queries
  • Network I/O
  • Serialization
  • External APIs
  • Messaging

rather than treating “Java versus Go” as an ideological choice.

Kubernetes fundamentals and networking

10 questions
77 Explain a basic Kubernetes application setup.Tap to reveal

A typical setup includes:

  • A Deployment to manage stateless application pods
  • A Service to provide stable internal networking
  • An Ingress to expose HTTP routes externally
  • A ConfigMap for non-sensitive configuration
  • A Secret for sensitive values
  • Readiness and liveness probes
  • CPU and memory requests and limits
  • Horizontal Pod Autoscaler where appropriate
  • Persistent volumes for workloads that require storage

The deployment creates ReplicaSets, and the ReplicaSet maintains the required number of pods.

78 What is a pod?Tap to reveal

A pod is the smallest deployable unit in Kubernetes. It contains one or more containers that share the network namespace, IP address, port space, volumes, and lifecycle.

Most application pods contain one main application container, sometimes with sidecars for proxies, logging, or other supporting functions.

79 What is the difference between a pod and a deployment?Tap to reveal

A pod is a running instance of one or more containers.

A deployment manages pods declaratively. It handles the desired replica count, rolling updates, rollbacks, pod replacement, and ReplicaSet management.

I normally create a deployment rather than managing standalone pods.

80 How do microservices communicate inside the same Kubernetes cluster and namespace?Tap to reveal

For normal internal communication, I would expose each workload through a ClusterIP Service.

For example:

apiVersion: v1
kind: Service
metadata:
  name: order-service
spec:
  type: ClusterIP
  selector:
    app: order-service
  ports:
    - port: 8080
      targetPort: 8080

Within the same namespace another service can call:

http://order-service:8080

Kubernetes DNS resolves the service name to the Service's stable cluster IP, and the Service load-balances requests across its ready pods.

I would not call pod IP addresses directly because pods can be recreated and receive new IP addresses.

81 How do services communicate across namespaces?Tap to reveal

From another namespace, I would include the target namespace in the DNS name:

http://order-service.orders:8080

Or use the fully qualified service name:

http://order-service.orders.svc.cluster.local:8080

A short service name is resolved within the caller's namespace. Cross-namespace communication therefore requires the namespace-qualified name.

NetworkPolicies must also allow the required ingress and egress traffic. A default-deny policy can block both service traffic and DNS resolution unless explicit rules are provided.

82 When would you use a headless Service?Tap to reveal

I would use a headless Service when clients need to discover and communicate with individual pod endpoints rather than going through one virtual service IP.

Typical examples include StatefulSets, databases, broker clusters, leader-election systems, and applications performing client-side discovery.

For ordinary stateless Spring Boot services, a standard ClusterIP Service is normally the right choice.

83 What is an Ingress?Tap to reveal

An Ingress defines HTTP or HTTPS routing rules from outside the cluster to Kubernetes services.

For example, it can route /orders to the order service, /customers to the customer service, or different hostnames to different services.

An Ingress resource requires an Ingress controller, such as NGINX Ingress, Traefik, or a cloud-specific controller.

84 What is a ConfigMap?Tap to reveal

A ConfigMap stores non-sensitive application configuration separately from the container image.

For example:

data:
  LOG_LEVEL: INFO
  FEATURE_X_ENABLED: "true"

It can be injected as environment variables, command-line arguments, or mounted files.

This allows the same container image to run with different configuration in different environments.

85 Should passwords and API keys go into ConfigMaps?Tap to reveal

No. A ConfigMap is intended for non-sensitive configuration.

Sensitive values should use Kubernetes Secrets or, preferably in an enterprise environment, integrate Kubernetes with an external secrets-management system such as:

  • HashiCorp Vault
  • AWS Secrets Manager
  • Azure Key Vault
  • Cloud provider secret stores

I would also use RBAC, encryption at rest, workload identities where possible, and secret rotation, and avoid logging secret values.

Kubernetes Secret values being base64-encoded should not be confused with encryption.

86 Does updating a ConfigMap restart the pod?Tap to reveal

Not automatically in every setup.

If a ConfigMap is mounted as a volume, the files may eventually update, but the application must reload them.

If values are injected as environment variables, existing pods do not receive the new values. They must be restarted.

A common deployment approach is to include a ConfigMap checksum in the pod template. When the ConfigMap changes, the deployment template changes and triggers a rollout.

87 A service needs to handle 2,000 to 3,000 requests in parallel. How would you design it?Tap to reveal

The first thing I would clarify is whether that means 2,000 to 3,000 requests per hour, per second, or genuinely 2,000 to 3,000 concurrent requests. Those are completely different workloads.

If the requirement is thousands of concurrent requests, I would first determine where time is spent:

 ↓
Ingress / gateway
 ↓

Then address each layer.

Application

If the application is stateless:

  • Run multiple replicas
  • Use a Kubernetes HPA
  • Use appropriate concurrency
  • Consider Java virtual threads for blocking I/O workloads
  • Configure connection pools
  • Set timeouts
  • Add backpressure

Database

Analyse query plans, indexes, connection-pool size, lock contention, read replicas where appropriate, and caching.

Downstream systems

Protect them with circuit breakers, rate limiting, bulkheads, and timeouts.

Asynchronous work

If the caller doesn't require an immediate result:

And I would load test the complete system. Scaling a single bottleneck does not automatically scale the system.

88 The service currently has only one Kubernetes pod. What would you do?Tap to reveal

If the application is stateless, horizontal scaling is the obvious starting point:

             ┌ Pod 1
Service ─────┼ Pod 2
             ├ Pod 3
             └ Pod 4

I would use a Deployment with multiple replicas, a ClusterIP Service, an HPA, and appropriate requests and limits.

If the application requires sticky sessions, I would first ask why. Ideally I would externalize session state into something such as Redis, a database, or a signed client token. Then any pod can handle any request.

Stateless services are much easier to scale and recover.

89 The interviewer says the endpoint is called 2,000 times per hour. Is that high traffic?Tap to reveal

Not by itself.

2,000 requests per hour is only around:

0.56 requests/second

on average.

So I would clarify whether they mean average requests, peak requests, concurrency, or transactions performed per request.

For example, 2,000 requests/hour is very different from 2,000 concurrent requests or 2,000 requests/second.

I would avoid proposing Kubernetes scaling before understanding the workload.

90 I have an endpoint that executes 4,000 database transactions. How would you build it in Java?Tap to reveal

I would first challenge whether the HTTP request really needs to execute all 4,000 transactions synchronously.

If not, I would consider:

    ↓
Create job
    ↓
Kafka / queue
    ↓
Workers
    ↓
Process batches
    ↓
GET /jobs/{id}

This gives retry, backpressure, progress tracking, horizontal scaling, and failure isolation.

If all 4,000 operations must be processed, I would also look for opportunities to batch them rather than perform 4,000 individual database round trips.

For example, instead of:

4000 individual INSERTs

use JDBC batching:

batch 100
batch 100
...

I would use bounded concurrency. I would not simply create 4,000 virtual threads and fire them at the database, because the database connection pool and the database itself are bounded resources.

91 A large data volume must be processed weekly within 90 minutes, and the data changes daily. How would you design it?Tap to reveal

The first question I would ask is:

Why reprocess everything weekly if only part of the data changed?

I would try to move from full processing to incremental processing:

Daily changes
    ↓
CDC / watermark / modified timestamp
    ↓
Incremental staging
    ↓
Weekly processing only handles delta

Then I would:

  • Partition the data
  • Process partitions in parallel
  • Batch database operations
  • Make processing idempotent
  • Introduce checkpoints
  • Allow failed partitions to retry
  • Avoid one huge transaction
  • Measure throughput

Given a record count and the deadline, I can calculate the required sustained throughput:

Then load test against that target with headroom. For example, I might target completion within 60 to 70 minutes operationally rather than designing exactly to the 90-minute deadline.

If the data changes daily, preprocessing the delta daily may also substantially reduce the weekly peak.

Handling peak traffic

2 questions
92 A microservice receives peak traffic in Kubernetes. How would you handle it?Tap to reveal

I would first identify the actual bottleneck. It could be CPU, memory, database connections, thread pools, downstream services, ingress capacity, or external API limits.

For a stateless service, I would normally use several layers of protection.

Horizontal scaling

Configure a Horizontal Pod Autoscaler based on suitable metrics: CPU utilization, request rate, request latency, active requests, Kafka consumer lag, or queue depth. The HPA adjusts the replica count of workloads such as Deployments based on observed metrics.

Cluster capacity

Ensure the cluster has sufficient node capacity. Workload autoscaling may need to be combined with node autoscaling so that newly created pods have somewhere to run.

Traffic protection

Use rate limiting, backpressure, timeouts, circuit breakers, bulkheads, load shedding, request-size limits, and connection-pool limits.

Absorb asynchronous work

For workloads that do not need an immediate response, put work onto Kafka or a queue and scale consumers independently.

Reduce repeated work

Use caching where the data and consistency requirements allow it.

Prepare for sudden peaks

Autoscaling takes time. For known traffic peaks, I may pre-scale before the event, maintain minimum spare replicas, overprovision some node capacity, warm application and database caches, and run load and stress tests.

Kubernetes documents node overprovisioning as a way to reduce scheduling delays during sudden scaling events.

Finally, I would verify the complete path under load. Adding application replicas does not help if all replicas are blocked by the same database connection limit.

93 Would you scale based only on CPU?Tap to reveal

Not necessarily.

CPU is useful when CPU usage correlates with traffic, but it may not represent the real bottleneck.

For example:

  • An I/O-bound API may have low CPU but high latency.
  • A Kafka consumer should often scale based on consumer lag.
  • A queue worker may scale based on queue depth.
  • A gateway may scale based on requests per second or concurrent requests.
  • A Java service may have high memory use that does not fall quickly after traffic decreases.

I would choose metrics that represent service demand and saturation, then validate the behaviour through load testing.

Kubernetes memory consumption

3 questions
94 What is the difference between memory request and memory limit?Tap to reveal

The memory request is used by the scheduler to decide where the pod can run. The memory limit is the maximum memory the container is allowed to consume.

request → scheduler capacity planning
limit   → maximum container memory

If a container exceeds its memory limit, it may be terminated with an OOMKilled status.

Unlike CPU, memory cannot simply be throttled safely when the limit is exceeded.

95 What happens when a pod exceeds its memory limit?Tap to reveal

The container is usually killed by the Linux kernel's out-of-memory mechanism. Kubernetes may then restart the container according to its restart policy.

The pod may enter CrashLoopBackOff if the problem repeats.

I would verify this using:

kubectl describe pod <pod-name>

and check whether the previous container state shows:

Reason: OOMKilled
Exit Code: 137
96 How do you check memory usage for a pod?Tap to reveal

For current usage:

kubectl top pod <pod-name>

For container-level usage:

kubectl top pod <pod-name> --containers

I would also inspect:

kubectl describe pod <pod-name>
kubectl logs <pod-name> --previous
kubectl get events --sort-by=.metadata.creationTimestamp

For historical analysis, I would use metrics from Prometheus, Grafana, Datadog, or the cloud monitoring platform.

kubectl describe pod <pod-name> -n <namespace>

99 After confirming OOMKilled, what do you do?Tap to reveal

I would use three stages.

Stabilize

Temporarily increase the memory limit so the service remains alive long enough to collect diagnostics. I would adjust the memory request separately if scheduling assumptions are also wrong.

I would be careful not to present increasing memory as the final solution.

Diagnose

For Java I might enable:

-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/dumps

I would ensure /dumps uses storage that survives long enough for the dump to be collected.

Then collect a heap dump, GC logs, Java Flight Recorder data, APM metrics, and native-memory metrics.

Analyse for:

  • Unbounded cache
  • Static collections
  • ThreadLocal leaks
  • Huge persistence contexts
  • Unreleased buffers
  • Queue growth
  • Unexpected object retention

I would also check non-heap memory. The Kubernetes memory limit applies to the entire container, not only the Java heap.

Fix and verify

After fixing:

  • Load test
  • Run beyond the original failure period
  • Verify memory reaches a stable plateau
  • Measure GC
  • Right-size the memory request and limit

I would not automatically revert to the old memory setting. I would configure the container based on measured behaviour.

100 What would you check in the application when a Java pod keeps being OOMKilled?Tap to reveal

  • Incorrect JVM heap configuration

  • Too many concurrent requests

For a Java application, I would verify that the JVM is container-aware and inspect settings such as:

-Xmx

-XX:MaxRAMPercentage

The Java heap limit must leave room for non-heap memory, including metaspace, thread stacks, direct buffers, native libraries, JIT compiler memory, and garbage-collector structures.

101 The pod limit is 1 GiB. Should the Java heap also be 1 GiB?Tap to reveal

No.

The Java process uses memory outside the heap, including metaspace, thread stacks, direct buffers, native libraries, JIT compiler memory, garbage-collector structures, and JVM internal data.

If -Xmx is set to the entire container limit, the process can be killed even when the Java heap itself has not reached -Xmx.

As a starting point I may allocate perhaps 60 to 75 percent of the container limit to the heap, then measure actual non-heap and native usage:

-XX:MaxRAMPercentage=70

The exact ratio should be determined through profiling and load testing rather than a universal percentage.

102 What is CrashLoopBackOff?Tap to reveal

CrashLoopBackOff means a container repeatedly starts and fails, and Kubernetes is increasing the delay before restarting it again.

It is not the root cause. I would inspect kubectl describe pod, current and previous logs, the exit code, probe failures, missing configuration, permission errors, OOM events, and dependency failures.

103 Can a liveness probe cause repeated restarts?Tap to reveal

Yes.

If the liveness probe is too aggressive or checks a dependency that is temporarily unavailable, Kubernetes may repeatedly kill an otherwise recoverable application.

I separate the responsibilities:

  • Startup probe: allows slow startup
  • Readiness probe: decides whether the pod should receive traffic
  • Liveness probe: detects an unrecoverable process state

A liveness probe should normally verify the application's own health rather than every downstream dependency.

106 A Java service becomes slow, memory grows continuously, and the pod restarts every few hours. How would you investigate?Tap to reveal

I would first correlate memory growth, traffic, GC activity, thread count, and request latency.

  2. Compare heap usage with total container memory

  4. Capture a heap dump before termination

I would also check native memory because a stable heap does not rule out direct-buffer, thread, or native-memory growth.

107 Your Kafka consumer processes the same payment event twice. What would you do?Tap to reveal
